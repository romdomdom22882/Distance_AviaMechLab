## Техническое задание: ядро сайта

**Версия:** 1.1  
**Дата:** 2026-01-22  
**Цель документа:** зафиксировать функциональные и нефункциональные требования
к базовому ядру сайта.

---

### 1. Область работ
Ядро сайта включает:
- авторизацию и реавторизацию пользователей;
- регистрацию новых пользователей (только суперпользователи);
- профиль пользователя (просмотр и редактирование);
- единый визуальный стиль и структуру CSS;
- чат между пользователями с файлами и уведомлениями;
- мониторинг онлайн-статуса пользователей и времени в системе;
- админ-панель с визуальными индикаторами для приложений.

---

### 1.1 Платформа и архитектурные требования
1. Платформа разработки: **Django** (актуальная LTS-версия на момент старта).
2. Обязательно использование стандартных компонентов Django:
   - `django.contrib.auth` (аутентификация и права доступа);
   - `django.contrib.sessions` (сессии);
   - `django.contrib.admin` (админка как базовый интерфейс управления);
   - `django.contrib.staticfiles` (статические файлы).
3. Модель пользователя должна быть **кастомной** (custom user model),
   определенной на раннем этапе проекта, с уникальным `username`.
4. Проект должен быть разбит на приложения Django (apps) по доменам
   ответственности: пользователи, чат, админка/индикаторы, общие модули.
5. Медиафайлы (аватары, вложения чата) должны храниться в `MEDIA` с контролем
   доступа, статические файлы — в `STATIC`.
6. Шаблоны должны строиться на основе Django Templates с базовым шаблоном
   (например, `base.html`) и наследованием через `{% extends %}`.
7. Общие данные для шапки/подвала должны передаваться через контекстные
   процессоры или включаемые шаблоны (`{% include %}`).

---

### 2. Роли и доступ
**Роли:**
- **Пользователь** — доступ к личному профилю, чату, просмотру онлайн-статуса.
- **Суперпользователь** — доступ к админ-панели, регистрации пользователей,
  настройкам и визуальным индикаторам.

**Общие правила:**
- Все страницы ядра доступны только после авторизации.
- Админ-панель доступна только суперпользователям.

### 3. Функциональные требования

#### 3.1 Авторизация и реавторизация
1. Авторизация выполняется по **username** и **паролю** с использованием
   механизма `django.contrib.auth`.
2. Формат username: `фамилия.имя` латиницей, например `ivanov.ivan`.
   - Регистр букв не должен влиять на вход.
   - Username должен быть уникален.
3. Пароли хранятся в виде безопасного хэша, используя встроенные механизмы Django.
4. После успешного входа создается сессия (cookie), через Django sessions.
5. **Реавторизация**:
   - При истечении срока сессии требуется повторный ввод пароля.
   - При попытке доступа к админ-панели возможен запрос повторного ввода
     пароля, если последняя проверка была более N минут назад.
6. Ограничение по неудачным попыткам входа:
   - после 5 ошибочных попыток блокировка на 15 минут.

#### 3.2 Регистрация пользователей (только суперпользователь)
1. Регистрация доступна только через админ-панель суперпользователя
   (Django admin или отдельный интерфейс, ограниченный правами superuser).
2. Обязательные поля:
   - **Фамилия**
   - **Имя**
   - **Отчество**
   - **Username** (уникальный, `фамилия.имя` латиницей)
   - **Отдел** (связь с таблицей `Отделы`, один основной отдел)
   - **Телефон** (формат +7XXXXXXXXXX или внутренний номер по правилам)
   - **Аватар** (файл изображения)
   - **Метка действующей комиссии** (bool)
   - **Метка отделов** (связь с таблицей `Отделы`, множественный выбор)
3. Валидации:
   - Username: `^[a-z]+\\.[a-z]+$`, длина 3–50, уникальность.
   - Телефон: нормализованный формат, уникальность по необходимости.
   - Аватар: форматы jpg/png/webp, размер до 5 МБ.
4. Автогенерация username возможна по введенным ФИО, с возможностью
   ручной коррекции.
5. При создании пользователя требуется установка временного пароля
   и принудительная смена при первом входе.

#### 3.3 Профиль пользователя
1. Профиль отображает **всю информацию пользователя**:
   ФИО, username, отдел, телефон, аватар, метки комиссий и отделов.
2. Пользователь может редактировать профиль:
   - разрешено: телефон, аватар, отчество (при необходимости), метки
     (по правилам роли);
   - запрещено: username и основной отдел (только суперпользователь).
3. Изменения сохраняются с аудитом (кто и когда изменил).

#### 3.4 Визуальный стиль
1. Основные цвета интерфейса:
   - основной: `#002664`;
   - фон: белый;
   - текст: черный.
2. Шрифт: **Arial** (fallback: `sans-serif`).
3. Все компоненты должны соответствовать единому стилю
   (кнопки, формы, ссылки, уведомления).
4. Должны быть реализованы **шапка** и **подвал** сайта как общие
   переиспользуемые шаблоны (base layout) для всех будущих приложений.

#### 3.5 Организация CSS
1. В проекте должен быть **общий** `style.css` (глобальные стили, переменные,
   базовые компоненты).
2. Для каждого приложения/модуля создается **локальный** `style.css`
   с переопределениями и специфическими компонентами.
3. Порядок подключения:
   1) `normalize.css`
   2) общий `style.css`
   3) локальный `style.css` приложения
4. Подключение файлов осуществляется через `staticfiles`
   (например, `{% static '.../style.css' %}`).

#### 3.6 Чат между пользователями
1. Чат поддерживает:
   - текстовые сообщения;
   - изображения;
   - файлы.
2. Хранение файлов — через Django storage (локально или объектное хранилище)
   с контролем доступа.
3. Максимальный размер вложения: до 20 МБ (настраиваемо).
4. Для каждого сообщения фиксируются:
   - отправитель, получатель, время, тип сообщения, статус (отправлено/доставлено/прочитано).
5. Уведомления:
   - при новом сообщении отображается индикатор/бейдж на сайте;
   - возможно всплывающее уведомление (toast).

#### 3.7 Онлайн-статус пользователей
1. Система должна показывать список пользователей онлайн.
2. Онлайн определяется по тайм-ауту активности (например, 2 минуты).
3. Отображается **время нахождения в системе**:
   - старт сессии;
   - длительность активной сессии.
4. Допускается реализация онлайн-статуса и уведомлений через WebSocket
   (например, Django Channels) либо через polling.

#### 3.8 Админ-панель
1. Доступ только суперпользователям (Django permission `is_superuser`).
2. Наличие визуальных индикаторов для текущих приложений, например:
   - количество онлайн пользователей;
   - число активных сессий;
   - новые сообщения в чате;
   - состояние комиссий и распределений по отделам.
3. Возможность добавления новых индикаторов без изменения ядра.
4. Логи действий администраторов доступны суперпользователю.

#### 3.9 Шапка и подвал сайта
1. **Шапка сайта (header)** должна быть единым компонентом, подключаемым
   ко всем шаблонам приложений.
2. Содержимое шапки:
   - слева: логотип;
   - справа: ссылки на доступные приложения/модули;
   - дополнительные ссылки: **«О системе»** и **«Руководство пользователя»**.
3. Ссылки **«О системе»** и **«Руководство пользователя»** ведут на PDF-файлы.
   Загрузка/обновление PDF доступна только суперпользователям.
4. **Подвал сайта (footer)** также является общим компонентом.
5. В подвале должны быть ссылки: **«Замечания»** и **«Предложения»**.
6. Структура шапки и подвала должна позволять расширение без правок
   в каждом приложении (через базовый шаблон Django).
7. Логотип в шапке ведет на главную страницу.
8. Список ссылок на приложения формируется динамически
   (на основе прав пользователя).
9. Для ссылок в шапке/подвале должен быть предусмотрен активный статус
   текущей страницы (визуальное выделение).

#### 3.10 Документы и общие страницы
1. PDF-файлы **«О системе»** и **«Руководство пользователя»**:
   - хранятся как записи в модели документов (slug, файл, версия, дата обновления);
   - доступны для скачивания всем авторизованным пользователям;
   - загружать/заменять может только суперпользователь.
2. Формат файлов — только PDF, размер до 20 МБ (настраиваемо).
3. Разделы **«Замечания»** и **«Предложения»** реализованы как формы обратной связи
   с сохранением данных (пользователь, тип обращения, текст, дата, статус).

### 4. Нефункциональные требования
1. **Безопасность**
   - HTTPS обязателен.
   - Пароли хэшируются и не сохраняются в открытом виде.
   - Ограничение попыток входа.
2. **Производительность**
   - основные страницы — до 2 сек при 95-м перцентиле.
3. **Логирование и аудит**
   - логирование входов/выходов, изменений профиля, действий админов.
4. **Надежность**
   - устойчивость к потере соединения (повторные запросы для чата/онлайна).

### 6. Критерии приемки (кратко)
1. Пользователь может войти по username и паролю, а после завершения сессии
   требуется повторная авторизация.
2. Суперпользователь может зарегистрировать нового пользователя с полным набором
   полей и валидировать их.
3. Профиль пользователя показывает все данные и позволяет редактировать
   разрешенные поля.
4. Единый стиль (цвета, шрифт) применяется на всех страницах.
5. Работает чат с текстом и файлами, есть уведомления о новых сообщениях.
6. Отображается список онлайн-пользователей и время их нахождения в системе.
7. Админ-панель доступна только суперпользователю и отображает визуальные
   индикаторы.
8. Шапка и подвал отображаются на всех страницах приложений и
   переиспользуются через базовый шаблон.
9. PDF «О системе» и «Руководство пользователя» доступны всем
   авторизованным, загрузка доступна только суперпользователю.
10. Разделы «Замечания» и «Предложения» принимают обращения и сохраняют их.
11. Приложение mod_production содержит все указанные таблицы и отображается
    в админке с индикаторами и корректной обработкой файлов `ris` и `ss`.
12. Таблицы KiPostavSoftVerPo, KiZn, KiGdeIstor, KiZnSoft и KiPoIstor
    доступны в админке и используют корректные связи и статусы согласно
    требованиям.
